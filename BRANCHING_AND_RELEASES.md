# Branching and release workflow

The release path is `dev` → `staging` → `main`. GitHub Actions checks the Go
backend, frontend, and media service before promotion, and Claude reviews every
release PR into `main`. Render deploys production from `main` and staging from
`staging`.

| Branch | Runs where | Frontend | Go API | Database | Payments / KYC |
|---|---|---|---|---|---|
| `dev` | Your machine | `localhost:3000` | local (`localhost:8080`) or staging | local Postgres or a Neon dev branch | Paystack test, SmileID sandbox |
| `staging` | Render | `staging.scrowpoint.com` | staging API (its own Render service) | Neon `staging` branch | Paystack test, SmileID sandbox |
| `main` | Render | `scrowpoint.com` | `api.scrowpoint.com` | Neon production branch | Paystack live, SmileID production |

Staging must never share the production API, database, `JWT_SECRET` or live
Paystack keys — otherwise testing on staging changes real users' escrow data.

## What happens automatically

1. A push to `dev` runs the **Quality Gates** workflow: Go tests, vet and build;
   frontend lint and build; and Python media-service tests.
2. After those checks pass, **Promote dev to staging** opens or updates a PR
   from `dev` to `staging` and enables squash auto-merge. GitHub merges it only
   after the required `Quality Gates` check passes. Render redeploys staging.
3. Test on `staging.scrowpoint.com`, then open a PR from `staging` to `main`.
   **Quality Gates** and **Claude Review** both run on it. Claude posts inline
   comments and a summary, and the `Claude Review` check fails if it finds a
   blocking issue (security hole, wrong money movement, data loss or leak,
   outage). You merge once both checks are green.

## Testing locally against staging

The browser only calls same-origin `/api/*`; Next.js rewrites it server-side to
`CORE_BACKEND_URL`, so switching backends needs no CORS changes.

```bash
cp frontend-web/.env.example frontend-web/.env.local   # once, then fill in
npm --prefix frontend-web run dev:local     # local code + local Go API
npm --prefix frontend-web run dev:staging   # local code + staging Go API and data
```

`dev:staging` reads `STAGING_CORE_BACKEND_URL` from `frontend-web/.env.local`,
checks the API's `/health`, and refuses to point at the production API. Use it
to try frontend changes against real staging data before pushing. Note that
redirects generated by the backend (for example Paystack's return URL, from the
backend's `FRONTEND_BASE_URL`) still go to the staging site.

## AI review before main

**Claude Review** (`.github/workflows/claude-review.yml`) uses
`anthropics/claude-code-action@v1` with `claude-opus-5-5` by default. One-time
setup:

1. Install the Claude GitHub App on this repository: run `claude` in the repo
   and use `/install-github-app`, or install it from
   <https://github.com/apps/claude>.
2. Add **one** repository secret (Settings → Secrets and variables → Actions):
   - `CLAUDE_CODE_OAUTH_TOKEN` — runs on your Claude subscription. Create it
     with `claude setup-token`.
   - or `ANTHROPIC_API_KEY` — pay-per-use API billing from the Claude Console.
3. Optional: add a repository **variable** `CLAUDE_REVIEW_MODEL`
   (e.g. `claude-fable-5-2` for deeper but slower, pricier release reviews).
4. Open a test PR into `main` and confirm Claude comments and the check passes
   or fails as expected before making it required.

Run `/code-review` (or `/security-review` for payment and auth changes) in
Claude Code locally before pushing to catch issues earlier and cheaper.

## One-time GitHub repository settings

In **Settings → General → Pull Requests**, enable **Allow auto-merge**.

In **Settings → Actions → General → Workflow permissions**, allow GitHub Actions
to create and approve pull requests. The promotion workflow uses the built-in
`GITHUB_TOKEN`; no personal access token or repository secret is needed.

Create branch rules (Settings → Rules → Rulesets, or Branches → Branch
protection rules) for `staging` and `main`:

- Require a pull request before merging and require the **Quality Gates**
  check.
- For `main`, also require the **Claude Review** check. As the only
  collaborator you cannot approve your own PRs, so set required approvals to
  `0` and let the two required checks be the gate. Do not allow direct pushes,
  force pushes, or deletion. Keep yourself as a bypass actor only for genuine
  emergencies (e.g. Claude is unavailable during an outage fix).
- For `staging`, do not require a human approval; keep the required pull request
  and status check so the automated promotion can merge after CI passes.

If GitHub branch rules have not been enabled, the workflows can run but GitHub
cannot enforce the required-check gates. Keep Render's production services
configured to deploy from `main`.
